# Prediction API

FastAPI service that serves the models registered in MLflow under the name `clinical-progression`. It returns the probability that a phase transition succeeds, and the calibration data logged when each model was trained.

**All data are synthetic.** The models are trained on generated data with arbitrary coefficients: the probabilities say nothing about real clinical progression.

The live, always up-to-date reference is the OpenAPI document generated by FastAPI:

| What | Address |
| --- | --- |
| Interactive documentation (Swagger UI) | http://localhost:8000/docs |
| Alternative documentation (ReDoc) | http://localhost:8000/redoc |
| Machine-readable contract | http://localhost:8000/openapi.json |

This page explains the design and gives examples. When it and `/openapi.json` disagree, `/openapi.json` is right.

## Running

In Docker, as part of the stack (code mounted, reloads on change):

```bash
docker compose up -d --build api
```

Or on the host, against the containers:

```bash
uv run uvicorn azml_market.api.app:app --reload
```

The API needs MLflow (`MLFLOW_TRACKING_URI`, `http://mlflow:5000` inside compose, `http://localhost:5000` on the host) and at least one registered model version. It does not read MongoDB or Azurite.

## Models: aliases and versions

Every route that takes a `model` accepts either:

- an **alias**: `champion` (default), or `challenger` when a version has passed validation and waits for approval;
- a **version number**: `1`, `2`...

The alias is resolved on every request. When a new version is approved, the next request uses it, with no restart. Loaded models are kept in memory by version number: a registered MLflow version never changes, so the cache cannot go stale. The first request for a version downloads it from MLflow and takes a few seconds; the following ones are fast.

## Routes

### `GET /health`

Liveness check, does not touch MLflow.

```json
{"status": "ok"}
```

### `GET /models`

All registered versions, oldest first, with their aliases, validation outcome and test metrics.

```bash
curl -s http://localhost:8000/models
```

### `POST /predict?model=champion`

Probability of moving to the next phase, for 1 to 1000 transitions. The response says which version actually answered, so a caller can tell when the champion has changed.

Request body, one object per transition. All fields are required and no other field is accepted:

| Field | Type | Allowed values |
| --- | --- | --- |
| `from_phase` | string | `I`, `II`, `III` |
| `modality` | string | `small_molecule`, `monoclonal_antibody`, `antibody_drug_conjugate`, `cell_therapy`, `gene_therapy`, `peptide` |
| `indication_area` | string | `oncology`, `immunology`, `neurology`, `infectious_disease`, `rare_disease`, `cardiometabolic` |
| `sponsor_type` | string | `large_pharma`, `biotech` |
| `biomarker_selected` | boolean | |
| `orphan_designation` | boolean | |

These values come from the curation schema ([schema.py](../curation/schema.py)), so the API accepts exactly what curation lets into MongoDB.

```bash
curl -s -X POST "http://localhost:8000/predict?model=champion" \
  -H "content-type: application/json" \
  -d '{"transitions": [
        {"from_phase": "II", "modality": "monoclonal_antibody", "indication_area": "oncology",
         "sponsor_type": "large_pharma", "biomarker_selected": true, "orphan_designation": false},
        {"from_phase": "II", "modality": "monoclonal_antibody", "indication_area": "oncology",
         "sponsor_type": "large_pharma", "biomarker_selected": false, "orphan_designation": false}
      ]}'
```

```json
{
  "model_version": "1",
  "model_kind": "logistic",
  "model_ref": "champion",
  "predictions": [
    {"p_progress": 0.5502752566281648},
    {"p_progress": 0.41044100951935064}
  ]
}
```

`predictions` are in the same order as `transitions`. `model_ref` repeats what was asked for (`champion`), `model_version` is what answered (`1`).

### `GET /models/{model}/calibration`

The calibration data logged with the training run of that version, computed on its test set. Nothing is recomputed.

```bash
curl -s http://localhost:8000/models/champion/calibration
```

```json
{
  "model_version": "1",
  "model_kind": "logistic",
  "test_brier": 0.21805973737716736,
  "test_spiegelhalter_p": 0.47569977665493124,
  "truth_oracle_brier": 0.2169846341876401,
  "model_curve": [
    {"bin_lower": 0.1, "bin_upper": 0.2, "mean_predicted": 0.1984812058599777, "observed_rate": 0.0, "n": 3},
    {"bin_lower": 0.2, "bin_upper": 0.3, "mean_predicted": 0.2750444805612489, "observed_rate": 0.2105263157894736, "n": 19}
  ],
  "truth_curve": [
    {"bin_lower": 0.2, "bin_upper": 0.3, "mean_predicted": 0.259652140786713, "observed_rate": 0.1176470588235294, "n": 17}
  ]
}
```

(Curves shortened here.)

- `model_curve`: test rows grouped in probability bins of width 0.1 on the model's prediction. For each bin, the mean predicted probability and the observed progression rate. A well calibrated model has points near the diagonal. Empty bins are left out, and bins with a small `n` are noisy.
- `truth_curve`: the same, using the synthetic truth `p_true` as the prediction. It shows how far from the diagonal even the true probabilities land on this test set, through sampling noise alone.
- `truth_oracle_brier`: the Brier score of `p_true` on the test set, the best any model could reach there.
- `test_spiegelhalter_p`: p-value of the Spiegelhalter calibration test. Below 0.05, calibration is rejected.

`p_true` exists only because the data are synthetic. On real data none of the `truth_*` fields could be produced.

## Errors

| Status | When | Body |
| --- | --- | --- |
| 404 | `model` is neither a registered version nor an existing alias | `{"detail": "No model version or alias '9' for 'clinical-progression'"}` |
| 422 | The request body breaks the schema: unknown value, missing or extra field, empty list | FastAPI validation detail, one entry per problem, with the field location |

Example of a 422, for `from_phase: "IV"`:

```json
{"detail": [{"type": "literal_error", "loc": ["body", "transitions", 0, "from_phase"],
             "msg": "Input should be 'I', 'II' or 'III'", "input": "IV"}]}
```

## Contract with the Streamlit app

The Streamlit app ([ui/app.py](../../../ui/app.py)) does not import this package. It builds its form from `TransitionFeatures` in `/openapi.json` and reads the response fields documented above. Changing a field name or an allowed value here changes the contract; the contract tests of step 6 are meant to catch that.

## Limits

- No authentication. In Azure the service would sit behind Entra ID or an API gateway.
- Calibration data are the ones logged at training time, on that run's test set. They are not recomputed on new data.
- Predictions are not logged. A production service would record inputs, outputs and the model version, for monitoring and audit.
